# i18n (Localization)

> `react-i18next` + `i18next-icu` UI-text translation, shared across `ketcher-react` and `ketcher-macromolecules`.

## Responsibility

Translate both packages' UI chrome (toolbars, dialogs, context menus, Settings panel, component chrome, monomer library, RNA Builder) while leaving chemistry data (element symbols, bond-type names, MDL/SDF format codes, numeric/valence notation) untouched. Owns: resource loading and registration, the active-language switcher and its persistence, ICU MessageFormat interpolation, the reactive `dir` (LTR/RTL) attribute on the editor root, and the build-time toggle between an English-only bundle and a multi-language one.

## Public interfaces

- `packages/ketcher-react/src/i18n/i18n.ts` — the configured `i18next` instance (default export) plus:
  - `SUPPORTED_LANGUAGES: SupportedLanguage[]` — `{ code, label }` pairs for every registered language
  - `isSupportedLanguage(code)`, `getStoredLanguage()` — read/validate the persisted language
  - registers a `languageChanged` listener that persists the new language to `localStorage` under the `ketcher-language` key (SSR-safe)
- **Translation key convention**: `"namespace:key.path"` strings. `ketcher-react` owns six namespaces — `common`, `toolbar`, `toolbars`, `dialogs`, `components`, `settings` — each with a matching JSON file per locale under `packages/ketcher-react/src/locales/<locale>/<namespace>.json`. `ketcher-macromolecules` owns two more — `macromolecules` (always-visible chrome: toolbars, zoom, layout mode, ruler, properties, preview) and `macromoleculesDialogs` (modal dialogs, monomer library, RNA Builder, context menus) — under `packages/ketcher-macromolecules/src/locales/<locale>/<namespace>.json`. Cross-cutting duplicated strings (Cancel/OK/Apply, monomer-type labels) resolve through `common:` from either package.
- **`packages/ketcher-macromolecules/src/i18n/registerNamespaces.ts`** merges the two macromolecules namespaces into `ketcher-react`'s shared instance via `i18n.addResourceBundle(...)`, called once from `ketcher-macromolecules`'s own entry point. This is a one-way merge (`ketcher-macromolecules` reaches into `ketcher-react`'s instance) specifically to avoid a reverse `ketcher-react -> ketcher-macromolecules` source dependency — `ketcher-macromolecules` already depends on `ketcher-react` for UI primitives, not the other way around.
- `resolveTranslatableText<T>(value: T, t: TFunction): T` (`script/ui/utils/index.ts`) — the core resolution primitive. `t` is required (not optional) and always called on string input — there is no longer a key-shape pre-check or literal-text passthrough (an earlier anchored regex distinguishing "looks like a key" from literal text was removed; every `title`/`enumNames` value passed through this function must now be an explicit, registered translation key). A non-key string still "works" only because i18next's own missing-key fallback (`returnEmptyString: false` in `i18n.ts`) returns the input unchanged — this is relied upon, not a feature of this function.
- `getSelectOptionsFromSchema(schema, t)` (same file) — builds `{ value, label }` dropdown options from a JSON-schema-like `{ enum, enumNames }` shape, resolving each `enumNames[i]` through `resolveTranslatableText`. `t` is required; module-scope schema constants with no component/hook access (e.g. `MeasureInput`'s unit dropdown, `Analyse`'s decimal-places dropdown) must be rebuilt as a `useMemo(() => getSelectOptionsFromSchema(..., t), [t])` inside the component instead, with explicit `enumNames` translation keys added for values that were previously literal (e.g. `settings:units.*`, `common:decimalPlaces.n0`-`n7`).
- The shared `Label` component (`script/ui/component/form/form/form.tsx`) calls `resolveTranslatableText` on both `title` and `tooltip` automatically. This means **any** JSON-schema `title` string converted to a `"namespace:key"` value resolves with zero further plumbing, as long as it renders through the schema-driven `Field`/`Label` machinery — but anything that reads a schema's `title`/`enumNames` directly (bypassing `Field`/`Label`) does not get this for free and must resolve the key itself (see Constraint below).
- `Dialog`'s `buttonsNameMap` — button tokens (`'Cancel'`, `'OK'`) resolve automatically via `common:button.*` when no override is given; an explicit `buttonsNameMap={{ OK: 'Apply' }}`-style override bypasses that and must spell out `t('common:button.apply')` itself.
- **Build-time language flag** — `KETCHER_MULTI_LANGUAGE_BUILD` (compile-time constant via `@rollup/plugin-replace`, same mechanism as `NODE_ENV`, set in both packages' `rollup.config.mjs`). English-only is the default build (flag unset/`false`): `SUPPORTED_LANGUAGES` collapses to `[{ code: 'en' }]`, every non-English JSON import is tree-shaken out of both packages' bundles (verified by bundle-content grep, not just code review), and the Settings language switcher doesn't render (it's conditioned on `SUPPORTED_LANGUAGES.length > 1`). Setting `KETCHER_MULTI_LANGUAGE_BUILD=true` at build time opts into every supported language instead. The two rollup configs must agree — `ketcher-macromolecules`'s `registerNamespaces.ts` reads the same env var independently to decide whether to register its own non-English resource bundles.
- **Locale resources are generated, not hand-maintained.** `scripts/generate-locale-resources.mjs` in each package scans `src/locales/<code>/` for that package's namespace files (six for `ketcher-react`, two for `ketcher-macromolecules`) and writes `src/i18n/localeResources.generated.ts` — static JSON imports (required for the tree-shaking above; imports can't be conditional) plus `BASE_RESOURCES` ('en') and `EXTRA_LOCALE_RESOURCES` (every other locale with *every* namespace file present — an incomplete locale is skipped with a console warning, never partially included, since i18next would otherwise fall back to English per-missing-key with no visible signal that the locale is unfinished). `i18n.ts`/`registerNamespaces.ts` import only from the generated file and never hardcode a language list — adding or removing a language is "add/remove its `src/locales/<code>/` directory, run `npm run i18n:generate`," with no edit to either file. The generated file is committed (so a fresh clone's `jest`/`tsc` work without a codegen step first) but also regenerated automatically via each package's `prebuild`/`prestart`/`pretest` npm hooks. A language's Settings-switcher label is its own `Intl.DisplayNames` endonym, computed at runtime from the code — never hardcoded — except where that computed default would change an already-shipped label (`zh-CN` → "简体中文", not `Intl.DisplayNames`'s "中文（中国）"); see `i18n.ts`'s `languageLabel`. See `adr/2026-10-02-generated-locale-resources.md`.
- **Tree-shaking hazard specific to the generated file**: anything that reads `EXTRA_LOCALE_RESOURCES` (or constructs a non-English label string) *outside* a branch gated by `MULTI_LANGUAGE_BUILD` becomes a live reference Rollup can't drop, even if that code path is never actually reached in the English-only build — this bit a first version of `SUPPORTED_LANGUAGES` (a module-scope `Object.keys(EXTRA_LOCALE_RESOURCES)` leaked zero bytes of JSON but did leak the `'简体中文'` override string into the English-only bundle) and was caught only by re-running the bundle-content grep check, not by `tsc`/`eslint`/`jest`. Always re-verify with a grep after touching this logic — see Testing note below.
- **Translation coverage is checked at compile time.** Both generated resource files use `satisfies Record<string, typeof BASE_RESOURCES>` so TypeScript reports any complete locale that is missing an English namespace or translation key. This does not detect extra locale-only keys or mismatched ICU placeholders; verify those by hand. Two Jest suites that used to scan both packages' source for `t('ns:key')` literals, assert every key resolved in every locale with matching ICU placeholders, and fail on literal `title`/`label`/`placeholder`/`tooltip`/`aria-label`/`alt` strings in migrated directories (`i18n.test.ts`, `noHardcodedStrings.test.ts`) were deliberately removed; `jest.setup.js` no longer forces `KETCHER_MULTI_LANGUAGE_BUILD=true` either, since that override existed solely for these suites. See [adr/2026-10-01-crowdin-placeholder-protection-gap.md](../adr/2026-10-01-crowdin-placeholder-protection-gap.md): Crowdin's own QA warning + its "export only approved translations" project setting catch a corrupted placeholder before it reaches `download` output, but once something is approved there is no further automated check.
- **RTL groundwork**: new UI-chrome styling (Emotion `css`/`styled`, MUI `sx`, `.less`) uses logical CSS properties (`insetInlineStart/End`, `marginInlineStart/End`, `paddingInlineStart/End`, `borderInlineStart/End`, `textAlign: 'start'/'end'`) instead of physical `left`/`right` — pixel-identical in the current LTR-only app, but makes a future RTL locale a data problem instead of a rewrite. Excluded: anything computed from real screen/canvas coordinates at render time, and chemistry-domain values that only coincidentally read like directions (e.g. RNA Builder's 5′/3′ phosphate position).
- **`groupNameToTabLabelKey`/`groupNameToRnaEditorItemLabelKey`-style maps** (`ketcher-macromolecules`) — the pattern used whenever a value doubles as both display text and a functional key (Redux dispatch payload, `data-testid` suffix, category filter). The enum/constant itself (e.g. `MonomerGroups.SUGARS`, `RnaBuilderPresetsItem.Presets`) must stay a frozen, untranslated identifier; a separate `Record<EnumValue, translationKeySuffix>` map is resolved through `t()` only at the point of *display*, never assigned back to the functional value.

## Dependencies

- `react-i18next`, `i18next`, `i18next-icu` (ICU MessageFormat for `{placeholder}` interpolation, including pluralization-style count params)
- Locale generators use the installed `prettier` JavaScript API, resolving the output file's project configuration (including EditorConfig) before writing. They do not spawn `npx`, so generation works on Windows without a command-shell wrapper and formatting failures leave the existing output intact.
- Consumed indirectly by every `ketcher-react`/`ketcher-macromolecules` component that calls `useTranslation()`/`i18n.t()`, and by the two JSON-schema modules (`script/ui/data/schema/struct-schema.ts`, `sdata-schema.js`, `script/ui/data/schema/options-schema.ts`) that hold translatable `title`/`enumNames` values used across both the schema-driven dialogs and a handful of components that read the schema directly (see Constraint below)

## Dependents

- Every `ketcher-react` UI file that renders user-facing text: toolbars/toolbox, all dialogs (including the legacy `script/ui/dialog/*` tree — R-Group, S-Group Properties, Label Edit, Enhanced Stereochemistry, Abbreviation Lookup, Structure Library/template-attach — which predates and is independent of the schema-driven `script/ui/views/modal/*` dialogs), context menus, Settings, MonomerCreationWizard
- Every `ketcher-macromolecules` UI file that renders user-facing text: always-visible chrome (toolbars, zoom, layout mode, fullscreen, ruler, properties, preview), modal dialogs (RNA Builder, monomer/preset creation, properties), the monomer library (search, favorites, filters, group/tab headers), context menus

## Assumptions & constraints

- **Chemistry data is never translated**, even when it happens to share text with a translated UI label elsewhere. Concretely: `struct-schema.ts`'s `bond.properties.type.enumNames` (Single/Double/Triple/…) is read directly by `script/ui/action/tools.ts` for the bond toolbar's ICU interpolation and by the bond context menu — neither resolves through `t()`, so this array must stay literal English. Numeric/valence-notation `enumNames` (Roman numerals, plain digit strings, MDL/SDF codes) are likewise left untranslated as data, not language.
- **A JSON-schema `title`/`enumNames` field converted to a translation key only resolves automatically for consumers that go through `Field`/`Label` or explicitly call `resolveTranslatableText`/`getSelectOptionsFromSchema(..., t)`.** Any code that reads `schema.properties[x].title` or `.enumNames` directly — e.g. building a bespoke context-menu submenu from the schema at module scope — bypasses that resolution entirely and will render a raw `"namespace:key"` string in every language once the schema value is converted. When converting a schema file to translation keys, grep for every direct (non-`Field`) reader of its `title`/`enumNames` first.
- **`invalidMessage` schema fields are a special case**: the form validation error popup (`ErrorPopover`) renders `schema.invalidMessage` verbatim with no `t()` call. A plain-string `invalidMessage` therefore cannot be made to translate by turning it into a `"namespace:key"` string — it would just display the raw key. The fix is to make `invalidMessage` a zero-arg function that calls `i18n.t(...)` directly and returns the already-resolved string (the validator already supports `invalidMessage` being a function); this works because it's invoked fresh on every validation run, so it reflects whatever language is active at call time.
- **Module-level schema objects built outside a component** (e.g. a dialog's inline JSON schema, or a context-menu's derived submenu data) cannot use `useTranslation()`. Two patterns are used depending on whether the value needs to react to a live language change: (1) call `i18n.t(...)` once at module-evaluation time for values that are acceptable to freeze at whatever language was active on first import (e.g. `Automap`'s inline schema) — accepted but imperfect, since a later in-session language switch won't update it; (2) move the construction into a `useMemo(() => ..., [t])` inside the component and call it with the live `t` from `useTranslation()` (the correct fix, used for `AtomMenuItems.tsx`'s schema-derived context-menu submenu) — prefer this over (1) for anything the user can trigger repeatedly without a full reload.
- Persisted language and persisted document/editor settings are two independent systems: language lives in its own `localStorage` key and applies immediately outside the Settings dialog's Apply/Cancel flow, on purpose — a language switch is not something a user expects "Cancel" to undo.
- `ketcher-macromolecules` renders inside `ketcher-react`'s `<I18nextProvider>` (see `Editor.tsx`'s lazy `import('ketcher-macromolecules')`) and reuses the same shared `i18next` instance — there is one active language for the whole app, not one per package.
- **A generic, shared form component's own internal state must key off a stable identifier, never off translated display text** — discovered the hard way in `Accordion.tsx` (Settings dialog): its "which section starts expanded" `useState` seed and `MeasureInput.tsx`'s rendered label both need a component's stable `key`/resolved-title value, not the raw prop that happens to hold the (possibly translated) label. A merge that reintroduces the untranslated literal in place of the resolved value looks harmless in English (the two often read identically) but silently breaks per-locale behavior, and in `Accordion.tsx`'s case broke a Playwright suite's automation entirely (a test's own logic assumed a specific section auto-expands by `key`). When touching a shared, non-namespace-specific component that renders both a `title`/`label` and an internal identifier, double check which one each internal computation actually reads.
