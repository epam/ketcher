# Crowdin placeholder protection is real but soft and approval-gated — accepted as a known risk

## Decision

Adopting Crowdin as a translation platform proceeds. Our locale JSON files' `i18next-icu` single-brace placeholders (`{value}`, `{count}`, `{shortcut}`, etc.) are not visually highlighted as protected tags in Crowdin's string editor on a standard (non-Enterprise) plan, and the QA check that does catch a mismatch is a dismissible warning, not a hard block — but the project's "export only approved translations" setting means a human still has to explicitly approve a flagged string before it can reach the codebase at all. This residual, approval-dependent risk is accepted for now; revisiting the interpolation syntax (see Alternatives) is deferred.

## Context

A scoped, unconfigured Crowdin compatibility test (`crowdin.yml` at repo root, covering only `ketcher-react`'s `common.json` and `dialogs.json`, uploaded via `npx @crowdin/cli upload sources` to project `935331`) was run to answer: does our existing i18n file format work with Crowdin without changes? Findings, in the order discovered:

1. Opening `meta.about.version` ("Version {value}") in the string editor showed `{value}` as plain text, not a highlighted/protected tag — `crowdin.yml`'s `type: "json"` (the closest generic match for our flat-JSON shape) gives no visual placeholder affordance.
2. Deliberately mistranslating it to "Version for the new project {values}" (renaming the placeholder) and attempting to save triggered a QA warning: *"The translation is missing 1 placeholder from the source: {values}"* — so Crowdin **does** run a curly-brace placeholder consistency check on a standard plan, independent of the Enterprise-only Custom Placeholders editor-highlighting feature. The warning did not block saving — it was dismissed and the mistranslation was saved as-is.
3. Running `npx @crowdin/cli download` (default flags — `--export-only-approved` defaults to `false` on the CLI side) did **not** pull the broken string into `packages/ketcher-react/src/locales/zh-CN/dialogs.json`; the file still held the original correct `"version": "版本 {value}"`.
4. Checked Project Settings → Translations/Export in the Crowdin UI directly: **"Export only approved translations" is enabled** on this project. The mistranslation was saved but never approved, so the project-level export setting excluded it regardless of the CLI's own `--export-only-approved=false` default — confirming the export gate is enforced server-side per the project configuration, not by the CLI flag.
5. Repeated the whole test with a second, independent language (Spanish, `es-ES`) added purely for this check — not registered in ketcher's `i18n.ts`. This time the same mistranslated "Version for the new project {values}" string was deliberately **approved** before downloading, and it *did* come through in `locales/es/dialogs.json` — confirming the gate is exactly approval-status-dependent, not language-specific or inconsistent: unapproved is blocked, approved passes through unchanged (QA warning or not).

Two unrelated CLI quirks surfaced along the way, worth noting for anyone re-running this: `download --language <code>` must use Crowdin's own internal locale code (`es-ES`, not our mapped `es`) — passing an unrecognized code silently exports *all* approved languages instead of erroring, which is how an unwanted `zh-TW` folder (a target language configured on this project, unrelated to this test) ended up in the repo twice and had to be deleted. Separately, the `languages_mapping` config block (intended to rename `es-ES`'s output folder to `es`) did not take effect in practice — the CLI still wrote to `locales/es-ES/`, requiring a manual rename; not investigated further since it's cosmetic and doesn't affect the placeholder-protection finding.

6. Downloaded `es` files don't make Spanish appear in the app's Settings language switcher — this was raised as a suspected bug and isn't one. `packages/ketcher-react/src/i18n/i18n.ts` imports each locale's JSON files by explicit static `import` statements and types `resources`/`SUPPORTED_LANGUAGES` against exactly `{ en, 'zh-CN' }`; `SUPPORTED_LANGUAGES` (what the switcher renders) is derived from `resources`, nothing scans the `locales/` directory at runtime. A locale folder existing on disk is necessary but nowhere near sufficient — this is by design (see `crowdin.yml`'s own comment: the Spanish test is "NOT wired into ketcher's actual SUPPORTED_LANGUAGES/i18n.ts"), not a defect in the Crowdin round-trip.

Confirmed directly in Crowdin's own ICU Message Syntax documentation: Crowdin's ICU support is specifically single-brace (`{variable}`, matching our `i18next-icu` syntax exactly) — double braces (`{{variable}}`, i18next's own default) are explicitly documented as unsupported and will cause a syntax error. So the placeholder-protection gap found here is about generic `type: "json"` giving no special treatment to `{variable}`-shaped text, not about Crowdin's ICU engine rejecting our brace style — the two are independent facts.

## Alternatives considered

- **Crowdin Enterprise's Custom Placeholders** (organization-level regex defining what counts as a placeholder, enabled per-project) — would add editor-time highlighting on top of what's already confirmed working; not needed to close the actual gap found, since the approval gate already blocks unapproved content from export regardless of whether the editor visually highlights the mismatch.
- **`type: "react_intl"`** — Crowdin's built-in ICU-aware JSON format, confirmed to correctly handle single-brace placeholders — but expects each entry as `{ "key": { "defaultMessage": "...", "description": "..." } }`, not our flat `{ "key": "string" }` shape. Adopting it would mean restructuring every locale file, not just a Crowdin-side config change.
- **Switch `i18next-icu`'s interpolation to i18next's default double-brace syntax (`{{value}}`)**, then use `type: "i18next_json"` (purpose-built for exactly this syntax). Feasible — no full ICU plural/select grammar is used anywhere today, only simple named placeholders — but it's a project-wide interpolation-syntax change, not something to do just to unblock a test. Deferred to a later, deliberate pass.

## Rationale

The test was explicitly scoped as exploratory ("без налаштування пайплайнів", per the owner's request) — the goal was answering the compatibility question, not reaching a finished integration. The empirical result is better than the editor's lack of visual highlighting initially suggested: Crowdin's QA check *does* flag a curly-brace placeholder mismatch, and — on this project's current settings — a flagged-but-unapproved translation cannot reach `download` output at all. The remaining risk is narrower and human-dependent: a reviewer who approves a string despite the QA warning (or a future change to the "export only approved" project setting) would let a corrupted placeholder through, with no further automated check downstream. Given that, restructuring the locale file shape or interpolation syntax now isn't justified — the current combination of QA warning + approval gate is a working, if not foolproof, safety net.

## Consequences

- The export-only-approved gate is a **project setting**, not something `crowdin.yml` declares or enforces — it must be verified (not assumed) on any Crowdin project this config is pointed at, including if the project is recreated or a new one is used later.
- The QA warning is dismissible, so the gate's real strength depends on reviewers actually treating "missing placeholder" warnings as approval-blocking in practice, not just on the setting existing.
- There is still no automated backstop once content *is* approved and downloaded: the Jest suite that used to assert `en`/`zh-CN` placeholder parity (`packages/ketcher-react/src/i18n/i18n.test.ts`) was removed earlier in this same change set (see git history around 2026-09-30/10-01 on branch `4384-language`). An approved-but-still-wrong placeholder (e.g. a reviewer overriding the warning) would only surface as a runtime/visual bug.
- Before relying on Crowdin for real (non-test) translation work: confirm "export only approved translations" stays enabled on whichever project is used, and treat the QA placeholder warning as a hard review-blocker in team process even though Crowdin itself won't enforce that.
- At the time this gap was found, turning this Spanish test into a real feature would have also required manually editing `i18n.ts` to wire in the new language — raised separately as its own bug report and fixed by `adr/2026-10-02-generated-locale-resources.md` (locale resources are now generated from whatever's in `src/locales/`, not hand-listed). That fix doesn't change this ADR's finding: `es` still only has `common`/`dialogs` downloaded (missing `toolbar`, `toolbars`, `components`, `settings`), so the generator correctly skips it as incomplete rather than exposing a half-translated language.
